# 产品经理核心能力模型

产品经理不是某一项单一技能的专家，而是围绕“把技术转化为用户价值与商业成果”构建起来的 **T 型能力结构**。对于有深厚研发背景（系统编程、AI Agent / 实时智能体、端云协同与分布式架构）的转型者来说，你并不需要洗掉重来，而是要在已有的技术地基上搭建产品与商业的上层建筑。

---

## 一、 产品经理的 T 型能力模型

```
          ┌─────────────────────────────────────────────────────────┐
  横向广度 │  市场洞察 │ 用户研究 │ 商业模式 │ 交互体验 │ 数据分析 │ 项目协同 │
          └───────────────────────┬─────────────────────────────────┘
                                  │
                                  │  纵向深度（你的差异化壁垒）
                                  ▼
                        ┌───────────────────┐
                        │  硬核技术理解力    │
                        │ (AI Agent/系统架构/│
                        │   端云工程化边界)  │
                        └───────────────────┘
```

* **横向广度（通用 PM 基本功）**：保证你能独立完成从发现机会、定义产品、推动落地到商业验证的全闭环。
* **纵向深度（不可替代的长板）**：在 AI Agent（如端云协同 AI Audio Agent）、端侧 SLM 与云端大模型混合编排、AI Infra、开发者工具（DevTools）等高技术门槛赛道，纯文科/商科背景的 PM 往往搞不清端云分流路由、VAD 端点检测、Token 流式吞吐与状态机边界，而这正是你的降维打击区。

---

### 产品工作的两种主导范式：执行型与创造型

产品经理都要对用户价值和业务结果负责，但工作的核心矛盾并不相同。更准确地说，**执行型产品**与**创造型产品**不是互斥的岗位标签，而是两种主导工作范式：一个产品在不同生命周期、不同项目中，可能在两者之间切换。

| 维度 | 执行型产品工作 | 创造型产品工作 |
| :--- | :--- | :--- |
| 问题状态 | 用户、场景和商业模式相对明确，重点是把已验证方向稳定交付 | 问题、用户、方案或商业模式仍不确定，重点是发现值得解决的问题并验证新解法 |
| 核心任务 | 排优先级、控范围、保质量、提效率、推动协同和规模化 | 做用户与市场探索、提出价值假设、快速试验、验证 PMF 与商业可行性 |
| 主要证据 | 交付质量、采用率、转化率、留存、成本、SLA 和发布稳定性 | 真实行为、痛点强度、替代方案、实验结果、付费意愿和留存信号 |
| 主要风险 | 做不完、做不好、协作失控或规模化后成本失控 | 做出没人需要的产品，或过早把错误假设工程化 |
| 常见场景 | 成熟产品迭代、企业流程、支付与订单、平台能力、运营效率 | 新品类、0 到 1、技术驱动创新、未验证用户需求和商业模式探索 |

**执行型不等于需求传声筒。** 它仍然要求 PM 做取舍、定义结果和持续改进，只是外部不确定性较低，价值更多来自稳定地把正确的事情做好。

**创造型不等于凭灵感做产品。** 它要求把创造力转化为可验证的假设：先确认真实问题，再用访谈、原型、人工服务或小范围实验验证价值、可用性、可行性与商业可持续性；未经验证的想法不能直接升级为完整工程项目。

可以用一个简单判断来选择工作重心：**如果“做什么”已经基本确定，重点是“怎样更稳定、更高效地交付”，偏执行型；如果连“是否值得做、为谁做、用什么方式解决”都未确定，偏创造型。** 新产品通常先以创造型工作为主，找到可重复的价值后转向执行型；成熟产品也应保留少量创造型探索，避免只会优化旧路径。

因此，本章六大硬技能不是二选一：创造型工作更依赖市场洞察、用户研究、原型和实验；执行型工作更依赖 PRD、项目协同、数据运营和质量治理，但两者最终都要回到用户价值、商业结果和可验证证据。

## 二、 六大核心硬技能 (Hard Skills)

### 1. 需求挖掘与分析 (Requirement Analysis)
* **核心产出**：去伪存真的高价值需求池（Backlog）、JTBD 目标卡、RICE/Kano 优先级排序清单与《The Mom Test》非引导访谈提纲。
* **关键动作与方法论**：
  * **区分 Want 与 Need**：不要按用户随口提的“表面解法”做功能；用 5-Whys 深度挖掘底层的“真实目的（Jobs To Be Done, JTBD）”。
  * **痛感强度与频次定级**：高频刚需（止痛药）> 低频刚需（救命药）> 高频非刚需（休闲小吃）> 低频非刚需（锦上添花维生素）。
  * **量化优先级排序**：运用 RICE 评分框架（$\text{Score} = \frac{\text{Reach} \times \text{Impact} \times \text{Confidence}}{\text{Effort}}$）排定 MVP 裁决线，避免主观拍脑袋。
* **推荐 AI 与现代工具链**：
  * **原声采集与转录**：飞书妙记、Otter.ai、Whisper（精准提取客户原声并打上时间戳）。
  * **长上下文聚类**：Claude 3.7 / Gemini 2.5 Pro（10+ 篇访谈原声跨样本痛点聚类，识别高频负向情绪）。
* **内置 Agent 技能联动**：
  * **挂载技能**：[`pm-user-insight`](../.agents/skills/pm-user-insight/SKILL.md)
  * **一句话唤醒词**：
    > *“设计一份针对【车载与移动端 AI Audio Agent 核心用户】的《The Mom Test》非引导性访谈提纲”* 或 *“根据以下 5 份用户工单，用 RICE 模型帮我排定语音伴侣功能优先级并划定 MVP 裁决线”*
* **工程师避坑最佳实践**：
  * ❌ **反面陷阱**：直接问客户“如果我们做一个支持无锁多线程同步的功能，你会用吗？”（客户永远出于客气回答“会用”，但上线后绝不买单）。
  * ✅ **最佳实践**：必须锚定**过去具体发生的真实行为**——“请回顾上一次使用 AI 语音助手/Audio Agent 时，它由于识别延迟卡顿、听错意图或插话打断失败让您最抓狂的一次经历？当时您是如何临时补救的？”

### 2. 产品规划与 PRD 撰写 (Product Spec & Documentation)
* **核心产出**：工业级标准 PRD、业务状态机模型（State Machine）、Given/When/Then BDD 验收规格与架构/QA 红队自检清单。
* **关键动作与方法论**：
  * **坚守 Why & What 禁飞区**：定义业务背景、用户旅程、性能 SLA 与成功指标，绝不替研发写内部架构与数据结构。
  * **全状态机覆盖**：梳理初始化、加载中、正常运行、被打断、弱网降级、超时重试与异常恢复的全闭环分支。
  * **BDD 验收标准**：用 `Given [前置上下文] When [触发动作] Then [预期系统表现与状态迁移]` 编写无歧义的交付标准。
* **推荐 AI 与现代工具链**：
  * **文档与逻辑建模**：Claude 3.7、ChatPRD、Mermaid（Markdown 内嵌流程图与状态图）、Linear / Jira Specs。
* **内置 Agent 技能联动**：
  * **挂载技能**：[`pm-prd-copilot`](../.agents/skills/pm-prd-copilot/SKILL.md)
  * **一句话唤醒词**：
    > *“帮我写一份【端云协同 AI Audio Agent 毫秒级打断与弱网离线降级】的 PRD，并扮演毒舌架构师与 QA 总监进行红队边界挑刺”*
* **工程师避坑最佳实践**：
  * ❌ **反面陷阱**：在 PRD 中手痒写出 SQL DDL 建表语句、C++ SPSC 环形队列或内部线程池配置，惹恼研发且丢失商业视角。
  * ✅ **最佳实践**：输出分层交底——给设计只讲场景痛点与情绪诉求（Design Brief）；给研发只讲业务规则、数据生命周期与外部 API 契约（Functional Specs & BDD）；对未实测性能参数必须标注 `[待硬件基线实测]`。

### 3. 原型设计与交互表达 (Prototyping & UX)
* **核心产出**：根据验证目标选择低保真流程稿、高保真 Figma 交互稿、状态机图或单文件可交互 HTML/React 原型；AI Audio Agent 场景重点交付“用户旅程 + 状态模型 + 可点击行为验证”，而不是单纯追求视觉精度。
* **关键动作与方法论**：
  * **信息架构与视觉层级**：3 秒内让用户看懂核心价值与主操作入口（Primary CTA），减少页面认知负荷。
  * **动态可交互验证**：告别静态线框图，让抽屉、弹窗、筛选条件、状态流转都能真实点击。
  * **多状态自闭环**：每个界面必须显式定义正常态、空状态、加载态与报错降级态。
* **推荐 AI 与现代工具链**：
  * **用户旅程与信息架构**：FigJam、Miro、Whimsical（梳理场景、任务、页面层级与用户路径）。
  * **视觉与设计协同**：Figma、即时设计（高保真页面、组件规范、设计师协作与可用性评审）。
  * **状态、流程与架构表达**：Mermaid、[diagrams.net（draw.io）](https://app.diagrams.net/)、Axure（分别适合版本化文本图、精确布局的架构图和复杂交互逻辑）。
  * **AI 代码原型**：Claude Artifacts、v0.dev、Bolt.new、Lovable；适合模拟流式输出、打断、重试、离线降级等动态行为。
  * **快速前端技术栈**：Tailwind CSS CDN + Alpine.js / React CDN + Lucide 图标（零 `npm install`，适合在线快速演示）。
* **内置 Agent 技能联动**：
  * **挂载技能**：[`pm-prototype-builder`](../.agents/skills/pm-prototype-builder/SKILL.md)（协同 `ui-ux-pro-max`）
  * **一句话唤醒词**：
    > *“根据刚才的 PRD，帮我生成一个带【PM 评审状态切换器】的单文件可交互 HTML 原型；请覆盖正常、流式回复、被打断、离线降级和执行失败状态。若要求真正离线运行，请将依赖改为内联 CSS/JavaScript，不要依赖 CDN。”*
* **工程师避坑最佳实践**：
  * ❌ **反面陷阱**：沉迷配置 Vite、Webpack、TS 复杂工程，花了 2 天搭脚手架，结果原型还没跑起来；或者把 AI 代码原型说成 Figma、Axure、墨刀的全面替代品。
  * ✅ **最佳实践**：坚持 **Zero-Setup 单文件架构**作为快速验证方案，但不要把它当作所有场景的长期技术方案。根据验证目标组合工具：Figma 负责视觉和设计协同，Mermaid/Axure 负责流程与状态表达，代码原型负责动态行为，真实客户端 PoC 负责音频链路与性能指标。

#### 工具选择原则：不是取代，而是分层组合

不同工具验证的问题不同，不能用“AI 代码原型取代 Figma/Axure/墨刀”作为通用结论：

| 验证目标 | 推荐工具 | 主要产出 |
| :--- | :--- | :--- |
| 梳理用户旅程、任务和信息架构 | FigJam、Miro、Whimsical | 用户旅程、场景地图、页面层级 |
| 确认视觉层级和设计规范 | Figma、即时设计 | 高保真稿、组件、Design System、设计交接稿 |
| 表达复杂条件分支、状态机和系统架构 | Mermaid、diagrams.net、Axure | 状态图、时序图、端云拓扑、条件分支和交互规则 |
| 模拟 AI Agent 动态行为 | Claude Artifacts、HTML/React、Cursor | 流式输出、插话打断、工具执行、重试和错误恢复 |
| 验证真实音频链路与性能 | 本地 Demo、浏览器 Web Audio、客户端 PoC | TTFA、打断延迟、VAD 行为、设备和弱网表现 |
| 做真实用户可用性测试 | Figma Prototype、Web Demo、真实设备 | 任务完成率、误操作、理解成本和恢复路径 |

#### AI Audio Agent 的推荐原型工作流

```text
[用户场景与任务]
          ↓
[FigJam / Miro：用户旅程与信息架构]
          ↓
[Figma：页面结构、视觉协同与设计评审]
          ↓
[Mermaid / diagrams.net / Axure：Agent 状态机、端云拓扑与异常分支]
          ↓
[代码原型：流式输出、打断、离线与错误状态]
          ↓
[真实设备 PoC：TTFA、VAD、打断延迟与弱网验证]
          ↓
[回写 PRD、验收标准与指标]
```

#### 原型的验证边界

代码原型可以验证交互逻辑，但不能单独证明真实音频链路成立：

* 可以验证：页面信息架构、状态迁移、按钮行为、流式展示、错误恢复和用户任务路径。
* 不能直接证明：真实 TTFA、VAD 效果、端侧模型功耗、设备兼容性、弱网可用率和生产环境稳定性。
* **最佳实践**：在原型中使用 `[Mock 数据]` 或 `[待实测基线]` 标注未经验证的延迟、成功率和模型指标；涉及音频体验的硬指标必须通过真实设备或可重复的实验环境验证。

Figma 也不是 PM 的禁区，Axure、墨刀和 diagrams.net 也不是无效工具。PM 可以用 Figma 验证信息架构和交互，用 diagrams.net 绘制端云协同架构与跨角色流程；设计师负责最终视觉系统与 Design Token。当状态数量、异步逻辑和数据联动明显增加时，再切换到代码原型或 Axure，避免为了工具偏好增加协作成本。

### 4. 数据分析与实验设计 (Data Analytics & Experimentation)
* **核心产出**：三层指标体系架构图（北极星 + 过程漏斗 + 反向护栏）、埋点规范文档（Tracking Spec）、漏斗与留存 SQL、A/B 实验评估报告。
* **关键动作与方法论**：
  * **指标三层塔设计**：
    1. **北极星指标**：衡量用户获得的真实价值（如每周高质量语音交互对话轮数或无故障陪伴时长），非虚荣浏览量。
    2. **漏斗过程指标**：各转化节点的流失率与耗时。
    3. **反向护栏指标**：崩溃率、首包播放延迟（TTFA P95/P99）、语音打断失败率、退订投诉量（绝对不能恶化）。
  * **同期群留存（Cohort Analysis）**：观察不同入流批次用户的日/周留存曲线是否走向水平底线（PMF 验证标志）。
  * **因果推断与 A/B 实验**：样本量估算（Power Analysis）、双尾显著性检验（$p < 0.05$），杜绝偷看效应（Peeking Problem）。
* **推荐 AI 与现代工具链**：
  * **数据引擎与分析**：ClickHouse、PostgreSQL、Metabase、Grafana。
  * **AI 数据 Copilot**：Claude Code、Python（`pandas` + `scipy.stats`）、Julius AI。
* **内置 Agent 技能联动**：
  * **挂载技能**：[`pm-data-analyst`](../.agents/skills/pm-data-analyst/SKILL.md)
  * **一句话唤醒词**：
    > *“写一段 PostgreSQL 语法的新功能 7 日留存 Cohort 分析 SQL”* 或 *“排查为什么今天 AI Audio Agent 首包音频播放延迟（TTFA）P95 恶化了 350ms”*
* **工程师避坑最佳实践**：
  * ❌ **反面陷阱**：只盯技术层监控（如 CPU 占用 15%），忽视业务层流失；或者实验刚上线 2 天看到 $p < 0.05$ 就急于下结论上线。
  * ✅ **最佳实践**：实验必须跑满完整自然周期（通常 7~14 天），避免周期性效应；指标异动归因严格执行“四层漏斗排查法”（全局大盘波动 → 客户端版本/环境切片 → 业务路径漏斗断点 → 用户行为归因）。

### 5. 市场与竞品分析 (Market & Competitive Intelligence)
* **核心产出**：TAM/SAM/SOM 空间测算、竞品逆向拆解矩阵、定价策略逆向工程与未满足需求挖掘清单（Unmet Needs）。
* **关键动作与方法论**：
  * **超越功能清单的逆向拆解**：不仅比对竞品有什么按钮，更拆解竞品的 **ICP（理想客户画像）、销售导向（PLG vs SLG）、单价与计量单位（Billing Unit）、技术护城河**。
  * **真实差评情报挖掘**：抓取竞品在 G2、Reddit、GitHub Issues 上的差评，找出竞品“架构上无法轻易解决”的结构性痛点。
  * **市场三层空间测算**：自上而下与自下而上双向校准潜在市场总量（TAM）、可服务市场（SAM）与可获得市场（SOM）。
* **推荐 AI 与现代工具链**：
  * **实时情报与长研报**：Perplexity Pro、Deep Research、NotebookLM。
  * **差评与口碑监测**：G2、Capterra、Trustpilot、Reddit、Hacker News、GitHub Issues。
* **内置 Agent 技能联动**：
  * **挂载技能**：[`pm-market-competitor`](../.agents/skills/pm-market-competitor/SKILL.md)
  * **一句话唤醒词**：
    > *“联网调研【两款主流 AI Audio Agent 竞品】的端云协同分流架构、Token 定价模型与 Reddit/G2 差评痛点”*
* **工程师避坑最佳实践**：
  * ❌ **反面陷阱**：搞“功能 Checklist 打勾战”，觉得竞品有的功能我们都要有；或者沉迷开源项目代码，误以为开源等于商业成功。
  * ✅ **最佳实践**：深入研究竞品的“退款原因”与“销售被卡死环节”，找到**结构性差异化切口**（例如竞品采用按月席位收费，我们按调用量量化计费；或竞品依赖云端闭源，我们提供端侧隐私合规保底）。

### 6. 敏捷项目管理与协同 (Agile Execution)
* **核心产出**：路线图（Roadmap）、MVP 迭代发布计划（Sprint Backlog）、成果导向高管周报/月报、高情商需求拒绝与准入门槛规范。
* **关键动作与方法论**：
  * **需求切片与范围防护 (Scope Creep Guardrail)**：控制版本边界，用 Thin-slice 垂直切片（端到端打通一条链路），不做大而全的积木。
  * **金字塔汇报原则 (Pyramid Principle)**：高管沟通结论先行（TL;DR），重点汇报商业产出（Outcomes）而非过程投入（Outputs）。
  * **四步需求拒绝法**：面对业务方/老板插队伪需求时，遵循 **“共情倾听 → 摆明大局与机会成本 → 给出低成本绕行方案 → 设定量化准入标准”**。
* **推荐 AI 与现代工具链**：
  * **敏捷协同与追踪**：Linear、Notion AI、GitHub Projects、飞书/Slack 自动化集成。
* **内置 Agent 技能联动**：
  * **挂载技能**：[`pm-report-polisher`](../.agents/skills/pm-report-polisher/SKILL.md)
  * **一句话唤醒词**：
    > *“根据这周的 4 条零散研发日志，生成一份成果导向、量化结果突出的高管周报”* 或 *“帮我起草一份高情商拒绝销售临时插队加功能的话术”*
* **工程师避坑最佳实践**：
  * ❌ **反面陷阱**：周报写成流水账（“本周提了 8 个 PR、修了 12 个 Bug、开了 5 个会”），老板看完毫无感知；业务方一提需求就说“做不了”激发对立情绪。
  * ✅ **最佳实践**：汇报紧扣核心指标变化（如“上线端侧本地意图快环分流后，AI Audio Agent 首帧响应延迟 TTFA 降低 42%，离线可用率提升至 99.5%，达成本季度核心 OKR”）；拒绝需求时算账——“当前冲刺若插入该需求，将导致核心版本延期 2 周，预计影响 300 家客户上线，建议先通过后台脚本人工代跑验证 ROI”。

### 六大硬技能的两种落地方式：公司产品 vs. 独立开发

同一套产品能力，在公司和独立开发场景下的交付方式不同。公司产品强调**角色分工、决策同步和交接契约**；独立开发强调**验证速度、端到端闭环和最小文档成本**。不要把公司的会议、审批和文档数量原样搬到个人项目中。

#### A. 公司产品：输出什么、交给谁

公司环境下，PM 不应该把一份“大而全”的 PRD 发给所有人，而应根据对方要做的决策拆分交付物。以端云协同 AI Audio Agent 为例：

| 阶段 | PM 输出内容 | 主要交付角色 | 对方用它做什么 |
| :--- | :--- | :--- | :--- |
| 机会发现 | Opportunity Brief、目标用户、真实行为证据、JTBD、问题优先级 | 产品负责人、业务负责人、销售、客户成功 | 判断问题是否真实、是否值得投入，以及目标客户是谁 |
| 方案定义 | PRD、用户旅程、业务规则、非目标、成功指标、状态机 | 研发负责人、客户端、服务端、AI/模型、设计、QA | 判断做什么、不做什么，以及各状态如何闭环 |
| 交互表达 | Figma 页面、低保真流程、diagrams.net 架构/流程图、可交互代码原型 | UI/UX、客户端、前端、QA、业务评审人 | 统一信息层级、交互路径和异常状态，不替设计师决定最终视觉规范 |
| 研发交接 | BDD 验收标准、接口输入输出契约、数据生命周期、依赖与风险清单 | 客户端、服务端、AI/模型、测试 | 将业务要求转成可实现、可测试的外部行为，不规定内部类结构和线程模型 |
| 数据与上线 | 埋点 Tracking Spec、指标口径、灰度/回滚门槛、发布检查清单 | 数据、研发、QA、运维、客户成功、销售 | 判断是否可以发布、如何监控、异常时如何回滚和对外解释 |
| 上线复盘 | 指标报告、用户反馈、实验结论、问题清单、下一轮决策记录 | 产品负责人、研发、数据、业务负责人 | 判断继续扩大、修复、调整方向还是停止投入 |

**公司产品的角色交付要点：**

* **给产品负责人/业务负责人**：讲问题规模、用户价值、商业目标、投入产出和取舍，不要只讲功能列表。
* **给设计师**：给用户场景、任务目标、信息层级、状态触发点和情绪要求；视觉风格、组件和 Design Token 由设计师负责。
* **给研发**：给业务规则、外部行为、状态迁移、约束、数据生命周期和验收标准；不要在 PRD 中规定内部架构实现。
* **给 QA**：给主流程、异常分支、状态转换、权限、超时、重试、幂等和回滚条件；每条验收标准都应该可以被观察或测试。
* **给数据/运营**：给指标定义、事件触发、用户分群、统计窗口和护栏指标；明确哪些数据仍属于 `[待实测基线]`。
* **给销售/客户成功**：给用户价值、适用边界、已知限制、上线范围和客户可理解的变更说明，不要直接转发内部技术细节。

**公司版 AI Audio Agent 交付最小集合：**

```text
Opportunity Brief
      ↓
PRD + 用户旅程 + 状态机
      ↓
Figma / diagrams.net / 可交互代码原型
      ↓
BDD 验收标准 + Tracking Spec + 发布门禁
      ↓
灰度发布 + 指标复盘 + 决策记录
```

#### B. 独立开发者：自己是产品和开发，怎么走流程

独立开发者不需要模拟完整的公司组织结构，但必须保留关键决策证据。推荐使用“**一个问题、一条薄切片、一个可测指标**”的端到端循环：
完整的选题、验证、发布、经营与复盘方法见：[《独立开发者产品实战手册》](./07-independent-product.md)。

1. **定义问题**：用一句话写清目标用户、具体场景和当前替代方案。例如：“经常独处驾驶的用户，需要一个可以被自然打断、弱网仍能完成简单操作的 AI 语音伴侣。”
2. **验证需求**：访谈或观察 5～10 个目标用户的过去行为，记录他们最近一次遇到的问题、现有补救方式和实际成本。不要先展示你的方案再询问“是否喜欢”。
3. **确定 MVP**：只保留一个核心闭环，例如“唤醒 → 识别 → 回复 → 用户打断 → 恢复倾听”。明确写出 V1 不做的内容，例如复杂长期记忆、完整车控和多设备同步。
4. **先做风险 Spike**：优先验证最可能推翻方案的技术风险：麦克风权限、语音输入、流式回复、打断、离线保底、端云成本、隐私边界和目标设备兼容性。
5. **做低成本表达**：先用 FigJam/Miro 或 diagrams.net 梳理流程，用 Mermaid 固化状态机；需要视觉验证时使用 Figma，需要行为验证时使用 HTML/React 代码原型。
6. **打通一条 Thin Slice**：不要先做完整平台。先让一个真实用户在一台目标设备上完成一条端到端路径，并记录失败原因。
7. **加入最小埋点**：至少记录会话开始、语音识别成功、首包播放、用户打断、工具执行成功/失败、会话结束和错误原因。指标先围绕任务完成率、TTFA、打断成功率和成本。
8. **小范围测试和发布**：让 3～5 个真实用户完成指定任务，观察他们是否能独立完成；发布时保留日志、错误上报、隐私说明和回滚开关。
9. **按周复盘**：每周只回答三个问题：用户是否真的使用？哪一步失败最多？下一周哪个假设最值得验证？根据证据调整产品，而不是根据个人偏好堆功能。

**独立开发者的最小文档集合：**

| 文档 | 内容 | 建议工具 |
| :--- | :--- | :--- |
| 一页 Product Brief | 用户、问题、核心价值、MVP、非目标 | Markdown / Notion |
| 一张状态图 | Agent 状态、触发条件、成功和失败恢复 | Mermaid / diagrams.net |
| 一份实现 README | 本地运行、环境变量、设备要求、已知限制 | Markdown / Git |
| 一张指标表 | 事件、口径、目标、护栏、数据状态 | Markdown / Spreadsheet |
| 一份决策日志 | 做了什么决定、依据是什么、何时复查 | Git / Markdown |

独立开发的核心不是“不写文档”，而是只保留能帮助自己做决策、开发、测试和复盘的文档。**公司产品交付给不同角色，独立开发交付给未来的自己。**

## 三、 四大核心软技能 (Soft Skills)

| 软技能 | 为什么至关重要 | 工程师转型常见盲区 | 提升抓手 |
| :--- | :--- | :--- | :--- |
| **1. 用户同理心 (Empathy)** | 产品的本质是服务人，不是运行代码 | 容易觉得“用户怎么这么笨，这都不会用” | 每月至少旁听 3 次真实用户操作或客户访谈，观察他们卡住的瞬间 |
| **2. 沟通与说服力 (Influence)** | PM 是“没有人事权的 CEO”，靠共识驱动全员 | 喜欢只讲干巴巴的技术逻辑，忽视对方的立场与利益 | 沟通前先想清楚：这件事对对方（研发/销售/老板）有什么好处？遵循“结论先行（金字塔原理）” |
| **3. 优先级决断力 (Prioritization)** | 资源永远稀缺，PM 最大的价值体现在“决定不做什么” | 容易老好人，业务方提什么都接，导致团队疲于奔命 | 学会用数据和 ROI 温和而坚定地 say no：“不是不做，是在当前阶段 A 的收益是 B 的 5 倍” |
| **4. 商业敏感度 (Business Acumen)** | 产品最终要实现商业可持续（赚钱或省钱） | 只看功能好不好玩，不看获客成本(CAC)和生命周期价值(LTV) | 养成拆解任何产品商业模式的习惯：谁买单？为什么买单？毛利率大概是多少？ |

## 四、 工程师转 PM 的优势放大与短板补强

### 如何把你的技术背景变成“核武器”？
1. **极速的技术可行性与成本预判**：在和客户或业务方开会的当场，别人还在记笔记，你已经能判断出哪些需求改配置就能上、哪些涉及底层架构重构，当场就能引导需求收敛。
2. **极高质量的异常边界定义**：普通 PM 写 PRD 往往只写 Happy Path（正常主流程），到了研发阶段漏洞百出；你对状态机、异步回调、弱网重试、幂等性了如指掌，写出的 PRD 研发极其信服。
3. **跨界翻译官**：你能把晦涩的底层技术指标（如端到端首帧播放延迟 TTFA、VAD 端点静音阈值、端侧 SLM 显存常驻与云端 TTFT 流式首包）精准翻译成用户能感知的交互体验与商业价值。

### 需要刻意克制与补强的短板
1. **戒掉“手痒帮研发设计实现细节”**：告诉研发“我们需要在端侧离线或弱网时，车控指令 150ms 内本地执行闭环，且 AI 回复在被打断时 80ms 内截断音频”即可，不要在 PRD 里强制规定研发必须用哪种具体的 LiteRT 算子、JNI 线程锁或环形缓冲区，除非这是产品对外的硬性合规标准。
2. **补齐商业化与运营视角**：多跟销售（Sales）、客户成功（CSM）、市场运营（Marketing）吃饭聊天，了解客户在掏钱签合同前真正在纠结什么。

## 五、 精选必读书单与核心精髓速查（按阅读优先级排序）

> **写在前面**：如果你日常精力有限，无法完整通读全书，请先通读以下每本书提炼的**核心命题、击碎的工程惯性与实战抓手**。这 6 本经典（+1 本访谈扩展）覆盖了从角色定位、验证闭环、交互直觉、成果导向、数据度量到向上沟通的全套底层体系。

---

### 1. 《启示录：打造用户喜爱的产品》(Inspired — Marty Cagan)
* **核心命题**：优秀产品经理的本质是**交付业务成果（Outcomes）**，而不是当“记录需求并排期上线的传话筒（Feature Team / Backlog Administrator）”。
* **击碎的工程惯性**：
  * 误把 PRD 当成向研发发号施令的交付契约，以为写完文档扔给研发就算完成任务；
  * 误将“技术可行性（Feasibility）”当成项目成立的唯一标准，忽略了“用户真正在乎并愿意买单（Value & Viability）”的前提。
* **核心方法论与实战抓手**：
  * **四大风险前置消杀原则**（写第一行生产代码前必须闭环验证）：
    1. **价值风险 (Value Risk)**：用户真觉得有价值吗？愿意掏钱购买或花时间使用吗？
    2. **可用性风险 (Usability Risk)**：小白用户能否自己搞明白怎么用？操作摩擦力是否足够低？
    3. **可行性风险 (Feasibility Risk)**：我们的工程师和技术栈在预算与排期内做得到吗？（工程师背景的固有优势）
    4. **商业可行性风险 (Business Viability Risk)**：商业模式、合规风控、销售渠道、法务与财务是否通得过？
  * **双轨敏捷 (Dual-Track Agile)**：产品探索（Discovery，低成本验证假设）与产品交付（Delivery，高质量写代码）并行。

---

### 2. 《精益创业》(The Lean Startup — Eric Ries)
* **核心命题**：面对极端不确定性的市场环境，最核心的竞争力不是“完美执行长期计划的速度”，而是**跑通“构建 - 测量 - 学习（Build-Measure-Learn）”反馈循环的单位时间成本**。
* **击碎的工程惯性**：
  * **“憋大招闭门造车”**：工程师本能地倾向于先把高可用、微服务、高并发架构全搭好再上线，往往耗时半年才发现根本没人需要这个功能；
  * **沉没成本偏执**：自己亲手设计并敲出的系统架构，即使上线后数据惨淡也舍不得砍掉或大幅调整。
* **核心方法论与实战抓手**：
  * **MVP（最小可行产品）**：不是质量粗劣的残次品，而是**验证核心商业假设所必需的最轻量化载体**（甚至可以是一张表单、一封冷邮件、手工后台干活的 Concierge MVP 或静态落地页）；
  * **经证实的认知 (Validated Learning)**：衡量研发团队进度的绝对指标不是“发版了几个接口/功能”，而是“通过真实行为数据证实或证伪了多少假设”；
  * **转型还是坚持 (Pivot or Persevere)**：核心假设被真实数据证伪后，保留核心认知资产，果断调整目标客群、收费模式或痛点切口，绝不盲目硬抗。

---

### 3. 《点石成金：访客至上的网页设计秘笈》(Don't Make Me Think — Steve Krug)
* **核心命题**：**可用性的第一法则是“别让我思考”**。界面上每多一个需要用户停顿半秒猜测“这个按钮能点吗”、“这段话什么意思”的元素，用户流失率就上升一个台阶。
* **击碎的工程惯性**：
  * **知识诅咒 (Curse of Knowledge)**：工程师转 PM 极其熟悉底层系统架构，下意识认为“这加个参数配置项、那多弹个设置窗口让用户自己选很合理”，却不知小白用户遇到选择就想关掉页面；
  * **“用户手册式”设计**：妄图通过弹窗引导、浮窗教程和几千字操作手册教会用户如何使用产品。
* **核心方法论与实战抓手**：
  * **用户是在扫视（Scan），不是阅读（Read）**：界面文案严禁长篇大论，遵循“先砍掉 50%，再砍掉剩下的一半”的精简原则；
  * **清晰的视觉层级三铁律**：越关键的功能视觉权重越大；逻辑相关的元素在物理空间上必须成组；逻辑包含必须通过嵌套或缩进明确呈现；
  * **游击可用性测试 (Discount Usability Testing)**：不要等大版本上线，随便找 3 个完全没接触过该系统的同事，给一个具体目标任务（如“找到历史账单并导出 PDF”），在旁边闭嘴观察他们卡在哪个按钮，5 分钟暴露 80% 的交互硬伤。

---

### 4. 《逃离构建陷阱》(Escaping the Build Trap — Melissa Perri)
* **核心命题**：把“交付功能数量（Outputs）”当成“创造业务价值（Outcomes）”是研发组织最大的慢性自杀；产品团队绝不能退化为按部就班的代码生产流水线。
* **击碎的工程惯性**：
  * **敏捷燃尽图崇拜**：研发团队每个两周 Sprint 的 Story Points 燃尽图极其完美、按时发版，但核心留存率和 ARR（年度经常性收入）毫无起色；
  * 认为“功能越多、产品越强”，无休止地堆砌边缘特性与定制需求。
* **核心方法论与实战抓手**：
  * **价值转化定义**：$\text{商业价值} = f(\text{用户痛点成功解决后支付的对价})$。没有改变用户行为、未能达成业务指标的代码，本质上全是系统负债与维护成本；
  * **产品卡塔 (Product Kata) 迭代循环**：
    $$\text{公司愿景} \longrightarrow \text{业务战略目标} \longrightarrow \text{当前现状度量} \longrightarrow \text{定位首要用户障碍} \longrightarrow \text{设计最小验证实验}$$
  * **战略沟通对齐**：向上管理只承诺“我们要解决的业务成果（如：缩短 30% 接入耗时、降低 15% 试用流失率）”，坚决不提前半年锁死具体功能交付列表。

### 5. 《精益数据分析》(Lean Analytics — Alistair Croll)
* **核心命题**：在产品当前所处的生命周期阶段，全团队只盯**一个关键指标（OMTM, One Metric That Matters）**，拒绝一切“自我感动的虚荣指标”。
* **击碎的工程惯性**：
  * **监控盲区与指标自嗨**：习惯像看服务器 APM 一样把所有数据都拉出几十个漂亮的折线图，迷恋“累计注册量”、“页面总 PV”等哪怕产品停运也会单调递增的数据；
  * 缺乏同期群留存（Cohort）意识，混淆了“相关性”与“因果性”。
* **核心方法论与实战抓手**：
  * **虚荣指标 vs. 行动指标 (Actionable Metrics)**：
    * *虚荣指标*：累计下载量、总注册数（无法指导决策，看起来好看但无用）；
    * *行动指标*：新用户次日/7日留存率、核心路径跳出率、付费转化率（指标异动能直接反推是哪个流程出了问题）；
  * **产品生命周期 5 阶段模型**：
    1. **移情 (Empathy)**：面对面定性访谈，确认痛点是否真实存在；
    2. **粘性 (Stickiness)**：打磨核心功能留存（**核心粘性不过关，严禁花钱买量与大规模推广**）；
    3. **病毒传播 (Virality)**：用户自发转介绍与口碑裂变（$K \ge 1$）；
    4. **营收 (Revenue)**：跑通单位经济学模型（LTV > 3×CAC）；
    5. **规模化 (Scale)**：标准化横向复制、拓展新市场或生态。

### 6. 《金字塔原理》(The Pyramid Principle — Barbara Minto)
* **核心命题**：人类大脑只接受**结构化的、自上而下的**信息输入；所有专业 PRD 编写、跨部门说服与向上汇报，必须做到**结论先行、纵向递进、横向分类**。
* **击碎的工程惯性**：
  * **排查流水账叙事**：工程师习惯“因为发生了 A，所以我尝试了 B，排查了 C，遇到了 D，最后我们应该做 E”，但在高管、销售与业务方听来毫无重点、极度低效；
  * 沟通时堆砌底层技术细节，缺乏全局业务收益概括。
* **核心方法论与实战抓手**：
  * **结论先行 (Top-Down Thinking)**：在任何文档与汇报的最开始给出 TL;DR 或最终定论；
  * **SCQA 开场架构**：
    * **S (Situation - 情境)**：双方已有共识的客观事实背景；
    * **C (Complication - 冲突)**：打破现状平衡的问题、瓶颈或风险；
    * **Q (Question - 疑问)**：面对这个冲突，我们必须解决的核心问题；
    * **A (Answer - 答案)**：我们的产品方案与关键决策；
  * **MECE 原则**（相互独立，完全穷尽）：拆解问题与论证方案时，横向子论点控制在 3~5 个以内，彼此不重叠、整体无遗漏。

### 💡 延伸实战必读：《妈妈测试》(The Mom Test — Rob Fitzpatrick)
*（注：本仓库用户研究、需求挖掘与访谈提纲设计的核心方法论来源）*
* **核心命题**：别问别人你的点子好不好（即使你的母亲出于爱也会对你说谎）；只探寻他们**过去真实发生的事实、经历与实际掏钱行为**。
* **击碎的工程惯性**：拿着自己构思的产品点子或原型向潜在客户做推销式访谈（“如果我做一个 XX 软件，只要 99 块钱你愿意买吗？”），收集回一堆虚假的客套认可。
* **三条不可违背的访谈铁律**：
  1. **严禁询问虚假假设**：永远不要问“如果未来有……你会不会用”，只聊他们**过去和当下已经在做的事**；
  2. **追问过去的付费与行动事实**：“上一次遇到这个问题是什么时候？当时你是怎么一步步解决的？花钱买过什么工具？有哪些环节让你崩溃？”；
  3. **少说多听，绝不推销**：访谈中 PM 发言时间严禁超过 20%。如果客户从没主动花钱或花大精力尝试解决过该痛点，直接判定为**伪需求**。
