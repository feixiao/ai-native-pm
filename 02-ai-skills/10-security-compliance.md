# AI 辅助安全合规需求产品化

"合规是法务的事，等法务出意见再说"——这句话让大量产品在上线后被迫返工：补同意界面、改删除流程、下架跨境功能。合规不是法务的独角戏，也不是研发的隐性成本，而是**产品需求的一部分**：数据怎么分级、保留多久、怎么删除、如何取得同意，都是产品决策。

作为工程师转型的 PM，你的边界要卡死：**你写契约（What & Why），研发写实现（How），法律结论归法务**。借助 AI（Claude Code / Cursor + 对应 `pm-security-compliance` Agent Skill），你可以把"数据安全、隐私合规"的法务黑话，翻译成研发可直接验收的需求契约——而不是越俎代庖输出建表语句和密码学方案。

> 对应 Agent Skill：`pm-security-compliance`（Claude Code / Cursor 安装后自动激活）；契约归档交 `pm-prd-copilot`，同意/删除埋点联动 `pm-data-analyst`，营销触达频控联动 `pm-operations`。

## 一、 数据分级与生命周期契约：四元组缺一即不合格

先分级，再谈保护。无标注的数据**默认敏感**，严禁默认公开：

| 级别 | 定义 | 示例 | 契约深度 |
|:---|:---|:---|:---|
| 公开 | 用户主动公开 | 公开帖子、头像 | 基础 |
| 内部 | 不可识别个人 | 匿名化行为统计 | 标准 |
| 敏感 | 可识别个人 | 聊天记录、邮箱、设备 ID | 四元组 |
| 高危 | 生物 / 支付 / 未成年 | 指纹、卡号、儿童数据 | 四元组 + 最高红线，标注 `[待法务确认]` |

每类数据必须写明四元组：**采集目的 → 保留期限 → 超期动作（删除/匿名化/归档）→ 跨境传输（是/否 + 机制）**。目的限定严禁"未来可能有用"这种兜底条款。

#### 提示词模板：存量数据四元组契约补全
```markdown
我的产品当前采集以下数据（含埋点事件）：[列出字段/事件清单，含使用场景]。
目标市场：[中国大陆 / 欧盟 / 美国 / 全球]，涉及 [是否含未成年人 / 支付 / 生物特征 / 位置]。

请为每个数据项输出生命周期契约四元组表格（级别 / 采集目的 / 保留期限 / 超期动作 / 跨境与机制）：
1. 无标注项一律按"敏感"定级并说明判断依据；
2. 采集目的必须是具体产品功能，禁止"改进服务"类兜底表述，逐条改写；
3. 命中高危（生物/支付/未成年）的行标注 `[待法务确认]`，并单独列一张"必须人工确认"清单；
4. 明确边界：只输出业务语义层契约，不输出 DDL、加密算法或密钥管理方案（那是研发技术方案的内容）。
```

## 二、 隐私法规映射：辖区差异速查（写映射前必查）

映射表输出的是**可验收的约束清单**而非法律解读，每条标注辖区来源与 `[待法务确认]` 状态，严禁输出"本设计符合 GDPR 第 X 条"这类法律结论：

| 法规能力 | 产品约束（可验收） | 辖区差异要点 |
|:---|:---|:---|
| 知情同意 | 分粒度授权界面，无默认勾选，拒绝非核心不得阻断核心 | GDPR = 明确同意；PIPL = **单独同意**（敏感信息）；CCPA = 选择退出 (opt-out) |
| 被遗忘权 | 删除请求 → 30 天内全链路删除（含备份）→ 回执 | GDPR 未设固定天数；PIPL 实务按 15 个工作日；CCPA 15 天内确认 |
| 数据可携 | 用户可导出其全部个人数据（JSON/CSV） | 三辖区方向一致 |
| 跨境传输 | 跨境数据清单 + 机制标注（SCC / 境内化 / 不出境） | GDPR 看 SCC/充分性认定；PIPL 看安全评估/标准合同备案 |
| 审计问责 | 敏感数据访问与删除留审计日志，保留 ≥1 年 | 三辖区方向一致 |

**三个辖区的同意模型根本不同，严禁用同一套界面逻辑覆盖全部市场。**

#### 提示词模板：辖区合规约束清单生成
```markdown
我的产品将发布到 [中国大陆 + 欧盟]，功能包括 [登录 / AI 对话（用户输入会发送到大模型 API）/ 消息推送]，处理的数据见上一条四元组表。

请生成分辖区的合规约束清单（GDPR / PIPL 两栏）：
1. 每个功能 × 每个辖区：给出可验收的产品约束（界面行为、时限、文案要求），不输出法律条文解读；
2. 同意界面必须分粒度：核心功能最小同意 + 增值功能可选同意 + 敏感信息单独同意（PIPL）/ 明确同意（GDPR），画出授权矩阵；
3. 每条约束标注 `[待法务确认]` 与责任方（前端/后端/架构）；
4. 输出"合规影响最大的 3 个功能改动"，按实现成本排序，供排期使用。
```

## 三、 需求级威胁建模 (STRIDE)：只回答暴露，不回答防御

对每个对外暴露的功能走六类威胁（伪装 / 篡改 / 抵赖 / 信息泄露 / 拒绝服务 / 权限提升），产出风险登记表，严守交接边界：

1. **只回答"哪个功能暴露于哪类威胁"**，不回答"用什么技术防御"——严禁 PM 直接指定"用 AES-256 + HMAC"这类实现；
2. **风险定级**：高危（敏感数据 × 不可逆损失）必须在设计层面解决，中危进迭代排期，低危记录在案；**高危未决严禁进入原型评审**；
3. **交接物**：风险登记表（功能 × 威胁 × 定级 × 缓解要求）交研发输出技术方案，QA 按登记表验收。

示例行：`删除接口 | 抵赖 + 越权 | 高危 | 缓解要求 = 需二次认证并留审计日志（实现方式由研发定）`。

#### 提示词模板：需求级 STRIDE 风险登记
```markdown
这是本迭代新增/改动的功能清单：[列出每个功能 + 暴露面（API/端/第三方）+ 涉及数据级别]。

请对每个功能执行需求级 STRIDE 分析：
1. 六类威胁逐项判断暴露与否，说明暴露路径（用户如何触发 / 攻击者如何利用）；
2. 定级规则：敏感/高危数据 × 不可逆损失 = 高危；其余按概率 × 影响给中/低；
3. 输出风险登记表（功能 × 威胁 × 定级 × 缓解要求），缓解要求只写业务语义（如"需二次认证""留审计日志""默认拒绝"），严禁指定算法/协议/框架实现；
4. 标出所有高危未决项——它们将阻塞原型评审，列出必须研发先行澄清的问题清单。
```

## 四、 同意与删除流程：顺畅度本身就是合规健康度

1. **同意分层**：核心功能最小同意 + 增值功能可选同意，分别记录同意版本与时间戳（同意可过期，功能变更需重新取得）；
2. **红线（反 Dark Pattern）**：严禁默认勾选、捆绑授权、"全部接受"唯一按钮、拒绝入口藏三层菜单——此类设计在 GDPR 下直接无效，在国内个保法下同样违规；
3. **删除流程**：发起删除 → 风险告知（将失去 X）→ 确认 → 30 天宽限（可撤回）→ 全链路删除 + 回执；每个状态可埋点度量（交 `pm-data-analyst` 锁口径）；
4. **度量**：同意转化率、删除完成率、删除 P95 时长、宽限期内撤回率——**严禁为保留存率把删除流程做难**。

#### 提示词模板：删除流程状态机与暗模式审查
```markdown
这是当前的账号删除流程：[描述]，同意/授权界面：[描述或截图说明]。

请执行：
1. 按「发起 → 风险告知 → 确认 → 30 天宽限（可撤回）→ 全链路删除（含备份链）→ 回执」重绘状态机，标注每个状态的埋点事件与超时策略；
2. 同意界面暗模式审查：默认勾选 / 捆绑授权 / 拒绝入口层级 / 同意版本记录——命中任一项即输出违规风险与整改契约；
3. 输出度量口径：同意转化率、删除完成率、删除 P95 时长、撤回率，与 [05-data-analysis.md](./05-data-analysis.md) 时区/去重规则对齐；
4. 风险告知文案约束（告知什么、禁止什么话术），最终文案交设计/文案定稿。
```

## 五、 合规发布门禁与独立开发者最小合规集

**企业级发布门禁（五项缺一不放行）**：分级覆盖 100%（无未标注数据）、高危威胁全部有缓解方案、同意界面可用、删除路径可走通、审计日志开启——交 `pm-operations` 同步进发布 checklist。

**独立开发者最小合规集（五项齐备方可公开发布，缺项在 README 如实声明风险）**：

| # | 项 | 为什么是红线 |
|:---|:---|:---|
| 1 | **BYOK**（用户自带 Key，不经手其数据） | 把"数据处理者"角色让给用户，绕开大部分数据契约义务 |
| 2 | **最小化采集**（只埋必需事件） | 采集面 = 义务面，少采一个字段少一份契约 |
| 3 | **一键删除按钮** | 被遗忘权的最短实现，也是用户信任的可见信号 |
| 4 | **一页 ToS + 隐私政策** | 公开声明 = 义务上限的公开锚点，防止事后被扩大解释 |
| 5 | **无默认勾选** | 同意有效性的地基，改一处界面即可 |

**泄露响应固定流程**：确认范围 → 72 小时内向监管与受影响用户通报（时限按辖区，`[待法务确认]`）→ 止损动作 → 根因报告回流更新威胁登记表。PM 拥有"暂停发布 / 功能下线"的合规否决权，无需等技术侧同意。

## 六、 运营防坑铁律（合规版）

1. **契约不越界**：只写 What & Why（分级、目的、时限、机制），DDL / 加密算法 / 密钥管理全部交研发——越界写实现，出了事没人认账；
2. **不出法律结论**：永远输出"约束清单 + `[待法务确认]` 状态"，"符合 GDPR 第 X 条"这句话不属于产品经理；
3. **无标注 = 敏感**：分级缺省方向永远从严，公开必须显式声明；
4. **删除做难 = 违规**：删除流程的顺畅度是合规健康度指标，任何"挽留式删除"都回到 §四红线；
5. **存量审查先拉回契约层**：单次红队审查问题数 > 15 条即说明粒度已滑向研发 checklist，必须按四元组/登记表格式重新归类，严禁把实现细节当合规问题上报。
