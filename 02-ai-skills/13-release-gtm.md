# AI 时代产品发版护栏、灰度放量与 GTM 发布指南

> **对应技能**：`pm-release-gtm`（唤醒指令：`/launch` / `/release flag`）
> **核心目标**：打通“UAT 验收通过”到“生产环境安全放量”的最后一公里，让每次发布可控、可观测、可 60 秒回滚。

---

## 一、 独立开发者与企业团队的“发版盲区”

功能做好、UAT 过关之后，很多团队和独立开发者会直接把代码全量推上线然后发条朋友圈就不管了。常见灾难如下：
1. **无灰度一刀切上线**：一个小边界 bug 直接把 100% 用户的核心流程打崩，且没有开关可以瞬间回退；
2. **无账单熔断裸奔**：产品一不小心被社区转发爆火，结果 AI API 没配限流与日限额，一夜间信用卡被刷爆；
3. **Changelog 充满研发自嗨**：写了一堆 `Refactor db pool`、`Bump version`，真实用户根本看不懂新功能解决了自己什么问题；
4. **上线即失明**：忘了确认核心漏斗埋点是否成功上报，上线三天依然不知道究竟多少人跑通了核心闭环。

---

## 二、 发版四道硬门禁 (Go/No-Go Release Checklist)

执行 `/launch` 时，必须强制核验以下 4 项基线：

| 门禁维度 | 核心核验项 |
| :--- | :--- |
| **1. 回滚与开关** | 是否具备 60 秒内生效的 Feature Flag 降级开关或单二进制/路由回退指令？ |
| **2. 成本与防破产** | 涉及外部付费 API 时，Rate Limit、单日硬顶配额与异常告警是否已激活？ |
| **3. 可观测埋点** | 从曝光到核心价值动作（如“安装并跑通”）的关键埋点是否已在预发环境验收落库？ |
| **4. 合规与退路** | License 署名、作者下架通道、退款承诺链路是否真实可达？ |

---

## 三、 渐进放量与用户侧 GTM 包装

### 1. 渐进式放量节奏
- **Phase 0 (Dogfooding, 24h)**：内部/自己真机全流程跑通一遍；
- **Phase 1 (种子放量, 5% 或 10 位访谈者)**：观察核心动作成功率与报错率；
- **Phase 2 (扩大灰度, 25%→50%)**：确认支持工时与转化漏斗稳态；
- **Phase 3 (全量 GA, 100%)**：正式交接 `pm-operations` 启动常规增长循环。

### 2. GTM 首发资产三件套
1. **人话版 Changelog**：只讲“用户能获得什么新能力 / 修复了什么具体卡点”；
2. **首次 30 秒上手引导文案**：明确用户进入后第一步点哪里、预期产出什么；
3. **渠道首发帖草案**：去营销味、重实证对比的克制首发帖（适配 X / V2EX / GitHub / 即刻）。

---

## 四、 提示词实战模板

```markdown
请使用 `/launch` 为【项目名称 v1.0】制定发版与 GTM 计划：
1. 输出 Go/No-Go 上线门禁核对表与 60 秒极速回滚操作指令；
2. 设计针对种子用户到全量用户的渐进式放量梯度与熔断阈值；
3. 将这几条 Git commit 改写为面向用户的人话 Changelog 与一条克制的社区首发帖。
```

### 附：发版后首周观察红线
- 若核心漏斗在 48 小时内未见埋点事件回流，立即暂停渠道推广并排查埋点丢失；
- 若单用户客服求助耗时超过约定工时预算，优先通过补齐首次引导 Tooltip 拦截重复问题。
