# AI 辅助产品体验走查（UAT）与尼尔森可用性审计指南

> **对应技能**：`pm-ux-audit`（唤醒指令：`/uat` / `/audit ux`）
> **解决痛点**：弥补“代码跑通 / 原型画完”与“真实用户第一次上手不踩坑”之间的体验鸿沟。

---

## 一、 为什么 AI 写出的界面往往过不了真实 UAT？

用 Coding Agent 生成前端应用非常快，但默认输出常常存在大量“Happy Path 幸存者偏差”：
- **静默失败**：点击按钮没反应（例如非 HTTPS 环境下 `navigator.clipboard` 报错未捕获），用户以为页面卡死；
- **研发黑话外泄**：直接把 `500 Internal Server Error` 或 `unexpected token` 弹窗甩给用户；
- **死胡同状态**：打开弹窗却没有 `Esc` 关闭或遮罩点击关闭；筛选条件选中空分类后，页面一片白屏却没有“一键恢复全部”出口；
- **极端文本撑爆**：正常测试数据 4 个字看着很美，真实数据一行 60 个字母没空格直接撑穿卡片布局。

在代码合并或产品发布前，PM 与独立开发者必须执行一轮硬核的 **UAT 体验走查 (Product Walkthrough)**。

---

## 二、 尼尔森十大可用性与边缘压力检查清单

每次使用 `/uat` 走查页面时，技能会自动按以下矩阵逐项扫雷：

1. **状态可见性**：任何点击/复制/异步请求是否在 100ms 内给出视觉反馈（状态变更/Toast）？
2. **微文案人话化**：报错文案是否用用户语言解释“发生了什么 + 怎么解决”，而非代码堆栈？
3. **可逆性与打断自由**：能否随时返回、撤销、关闭弹窗（含 `Esc` 键）？动画中能否打断？
4. **防错与边界保护**：高危不可逆操作是否有缓冲确认？快速双击是否会发出重复请求？
5. **降级与容错**：断网、无权限、空数据、超长无空格字符串下，页面骨架是否依然完整不崩？
6. **窄屏与触控热区**：手机 375px 视口下按钮是否重叠、表格是否溢出？

---

## 三、 标准《UAT 体验走查缺陷单》交付规范

走查不是随口吐槽“这里不好看”，而是输出**带严重级、复现路径、违背原则与明确验收标准**的缺陷单：

| 级别 | 判定标准 | 发版裁决 |
| :--- | :--- | :--- |
| **P0 阻塞级** | 主干流程卡死、静默失败、数据丢失、移动端完全遮挡无法点击 | **🔴 阻塞打回**，绝对禁止上线 |
| **P1 严重级** | 无空状态引导、报错文案为纯技术异常、键盘 `Esc` 无法退出抽屉 | **⚠️ 修复后重验放行** |
| **P2 优化级** | 微文案不够地道、次级间距微调 | 记录入下个迭代池，不阻塞当前发版 |

---

## 四、 提示词实战模板

```markdown
请使用 `/uat` 对当前页面文件（如 `landing-page.html` 或 `src/App.tsx`）执行全链路体验走查：
1. 逐条对照尼尔森十大可用性原则，检查微文案、反馈延迟与可逆性；
2. 模拟以下 4 种边缘压力：剪贴板被拒、列表为空、100 字符超长文件名、375px 手机窄屏；
3. 输出《UAT 体验走查缺陷单》，明确 P0 阻塞项及对应修复验收标准。
```
