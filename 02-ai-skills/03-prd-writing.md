# AI 辅助 PRD 撰写与红队评审

写 PRD（产品需求文档）的目的绝不是为了“留档交差”，而是为了**在投入昂贵的研发资源写代码之前，以最低成本用文字和图表把所有业务边界、状态流转、异常分支彻底想清楚，并在团队内部达成零歧义共识**。

作为工程师出身的 PM，你在写 PRD 时拥有天然的降维打击优势：**你懂状态机、懂并发、懂网络不可靠性**。结合 AI 的结构化生成与“红队挑刺（Red Teaming）”能力，你可以把写一份高质量 PRD 的时间缩短 60%，同时让研发和测试在评审会上对你的专业度心服口服。

---

## 一、 工业级标准 PRD 黄金结构模板

不要写几十页没人看的散文式文档。一份让研发极度舒适的现代 PRD 应当像优秀的接口规范一样结构化：

```markdown
# [项目/功能名称] PRD

| 文档状态 | 草案 / 评审中 / 已基线(Baseline) / 已上线 | 负责人 | @Frank |
| :--- | :--- | :--- | :--- |
| **目标版本** | v1.2.0 | **优先级** | P0 |

## 1. 变更记录 (Changelog)
| 日期 | 版本 | 修改人 | 修改内容摘要（重点标出评审后变更项） |
| :--- | :--- | :--- | :--- |

## 2. 背景与目标 (Why)
- **业务背景与用户痛点**：谁在什么场景下遇到了什么问题？（附真实数据或客诉证据）
- **商业价值与不做的后果**：为什么现在必须做？
- **成功衡量指标 (Success Metrics)**：
  - 核心指标（如：功能渗透率 ≥ 20%，首帧耗时降低 30%）
  - 护栏指标（如：客户端崩溃率不上升、服务端 CPU 负载增幅 < 5%）
- **明确不做事项 (Out of Scope / Non-Goals)**：本期明确砍掉、留待后续版本的内容（极重要！）

## 3. 核心角色与业务流程 (Flow & State Machine)
- **核心角色权限矩阵**
- **端到端主流程图 (Mermaid Sequence / Flowchart)**
- **核心对象状态机流转表**（当前状态 + 触发事件 → 下一状态 + 副作用动作）

## 4. 功能需求详述 (What)
- **模块 4.1：[功能模块名]**
  - 原型图 / 交互说明
  - 字段规则与校验逻辑（类型、长度限制、默认值、空值展示）
  - **异常边界与降级处理 (Edge Cases)**：弱网超时、并发重复点击、权限失效、空状态、第三方服务挂掉时的表现
  - **验收标准 (Acceptance Criteria - Given/When/Then)**

## 5. 非功能性需求 (Non-Functional Requirements)
- **性能与 SLA 要求**：端到端响应延迟、并发峰值 QPS、弱网抗丢包指标
- **兼容性与安全合规**：端版本向下兼容策略、数据脱敏与鉴权要求

## 6. 数据埋点与实验设计 (Tracking & A/B Test)
- **新增埋点事件表**（事件名、触发时机、上报属性 Key-Value）
- **灰度发布与开关策略 (Feature Flag)**：如何分批放量？出现严重问题如何一键回滚？
```

## 二、 独门杀手锏：用 AI 做「需求评审前的红队挑刺」

很多 PM 最怕在需求评审会上被研发和 QA 问住：“如果用户在发请求瞬间断网了怎么办？”“如果两个管理员同时修改同一条配置怎么处理？”“老版本客户端收到新枚举值会崩吗？”

**解决方案：在把 PRD 发给研发团队之前，先让 AI 扮演“最毒舌的资深主架构师 + QA 总监”，对你的 PRD 初稿进行一轮无情的红队攻击（Red Teaming）。**

---

## 三、 即插即用提示词模板库 (Prompt Templates)

### 模板 1：从一句话粗糙想法生成结构化 PRD 初稿
```markdown
你是一位拥有 10 年经验的高级产品经理，兼具深厚的系统架构理解力。
我现在要为【产品名称】撰写一份关于【新功能名称】的 PRD。

以下是目前的粗糙背景与核心设想：
- **目标用户**：【谁使用】
- **核心解决的痛点**：【解决什么问题】
- **主流程设想**：【1... 2... 3...】
- **本期不做（如果有）**：【暂不考虑的内容】

请按照工业级 PRD 标准结构帮我生成一份详尽的 PRD 初稿，必须包含：
1. 背景、核心成功指标（Success Metrics）与护栏指标（Guardrail Metrics），以及明确的 Non-Goals。
2. 使用 Mermaid 语法绘制的主业务流程图（Flowchart 或 Sequence Diagram）。
3. 如果涉及状态变化，请绘制完整的【状态机流转表】（当前状态、触发事件、前置校验、目标状态、系统动作）。
4. 详细的功能逻辑说明，并使用 `Given [前置条件] / When [触发动作] / Then [预期结果]` 格式编写每项子功能的验收标准（Acceptance Criteria）。
5. 配套的数据埋点设计表（事件英文名、触发时机、核心属性参数）。
```

### 模板 2：红队审查 ① —— 模拟资深架构师与 QA 找边界漏洞（必用！）
```markdown
以下是我撰写的 PRD 初稿，准备明天提交给研发和测试团队开需求评审会：
<prd_draft>
[粘贴你的 PRD 内容]
</prd_draft>

请你现在切换到【红队挑刺模式】，同时扮演一位“极其挑剔、厌恶需求返工的资深后端/音视频架构师”和一位“专门找极端边界 Bug 的 QA 测试总监”。
请毫不留情地审查这份文档，并按以下分类列出所有潜在漏洞：

1. **逻辑闭环缺失与状态死锁**：哪些状态流转只有正向没有逆向？哪些操作中断后会停留在中间脏状态？
2. **极端异常与并发边界 (Edge Cases)**：
   - 网络层：弱网、高丢包、请求超时、断线重连后状态如何对齐？
   - 并发与幂等：用户狂点按钮、多端同时登录操作、多管理员同时修改同一资源会发生什么？
   - 极端数据：空数据、超长输入、特殊字符、越权访问、配额耗尽时界面展示什么？
3. **新老版本兼容与历史数据迁移**：老版本 App/SDK 遇到新协议字段会怎样？存量历史数据默认值怎么刷？
4. **研发在评审会上最可能追问的 5 个尖锐问题**：提前帮我列出来，并给出建议的产品回答方案。
```

### 模板 3：红队审查 ② —— 砍需求与 MVP 极简瘦身
```markdown
请审视下面这份 PRD 的功能范围：
<prd_draft>
[粘贴 PRD 功能列表]
</prd_draft>

假设研发负责人刚刚告诉我：“本周资源临时被抽调，给你的开发工时直接砍半，只剩 5 个研发人日，但下周五必须按时上线验证核心价值。”

请帮我用奥卡姆剃刀原则对这份 PRD 进行极简瘦身：
1. **核心价值闭环提炼**：哪 20% 的功能支撑起了 80% 的用户核心价值（Must-have）？
2. **无情砍刀清单**：哪些功能属于“过度设计”或“可以靠人工后台配置/运营话术临时顶替”的？请列出具体砍掉的模块及替代绕行方案（Workaround）。
3. **分阶段迭代路线**：给出调整后的 `V1.0 (5天极简MVP)` vs `V1.1 (后续补齐)` 划分表。
```

### 模板 4：自动补全数据埋点与 A/B 实验方案
```markdown
针对以下产品功能描述：
<feature_spec>
[粘贴功能逻辑描述]
</feature_spec>

请作为数据产品经理，帮我设计配套的数据追踪与实验验证方案：
1. **核心转化漏斗定义**：从用户看到入口到最终完成价值交付，分为哪几个关键漏斗节点？
2. **埋点事件规范表（Markdown 表格）**：
   - 列名：`事件编码 (snake_case)` | `事件中文名` | `触发精确时机` | `必传业务属性 (JSON 属性及类型说明)` | `用于计算的指标`
3. **A/B 实验设计方案**：
   - 核心假设（Hypothesis）：如果我们将 [改动X] 呈现给用户，那么 [指标Y] 将提升 [Z%]，因为 [原因]。
   - 实验分组与分流粒度（按 UserID 还是 DeviceID？为什么？）
   - 观察周期与提前熔断条件（出现什么异常指标立即关停实验？）。
```

### 模板 5：生成给高管/业务方看的 30 秒一页纸摘要 (Executive Summary)
```markdown
我的完整 PRD 较长且包含大量技术与状态细节。现在我需要向公司高管、销售总监和市场团队同步这个新特性。
请将以下详细 PRD 提炼并翻译成一份【零技术黑话、纯商业与用户价值导向的 Executive Summary（300字以内）】：
<prd_content>
[粘贴 PRD]
</prd_content>

输出包含：
1. **一句话总结 (TL;DR)**：我们做了什么，为谁解决了什么痛点？
2. **三大商业收益 (Business Impact)**：对获客、留存或变现有什么具体帮助？
3. **上线时间与配合事项**：什么时候可用？需要销售/运营团队配合做什么？
```
